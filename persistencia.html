Definición

La persistencia de datos es la capacidad de una aplicación para guardar su información de forma que no se pierda al cerrar la app o apagar el dispositivo. El acceso a datos son las técnicas y herramientas que usa la aplicación para leer, insertar, modificar y eliminar esa información.

Características

  • Durabilidad: los datos siguen existiendo después de cerrar la aplicación.
  • Recuperación: se pueden consultar después cuando se necesiten.
  • Integridad: los datos deben mantenerse correctos y consistentes.
  • Seguridad: se debe controlar quién puede leerlos o modificarlos.
  • Eficiencia: en un móvil hay que cuidar la batería, el espacio y la velocidad.
  • Disponibilidad sin conexión: muchas apps deben funcionar aunque no haya internet.

Formas de persistencia en dispositivos móviles

a) Archivos

La app guarda información directamente en archivos del dispositivo. En Android hay varias opciones:

  • SharedPreferences / DataStore: guardan pares clave-valor pequeños (configuraciones, tema oscuro, si el usuario ya inició sesión).
  • Almacenamiento interno: archivos privados de la app (filesDir). Otras apps no pueden verlos.
  • Almacenamiento externo / compartido: fotos, descargas, documentos que el usuario puede ver desde otras apps.
  • Caché: archivos temporales que el sistema puede borrar.

Formatos de archivo comunes: texto plano, JSON, XML, CSV, imágenes, etc.

b) Bases de datos locales

Guardan información estructurada dentro del dispositivo. La más usada es SQLite, una base de datos relacional ligera integrada en Android e iOS. Se usan tablas, filas, columnas y consultas SQL. En Android se suele acceder con la biblioteca Room, que trabaja encima de SQLite. Otras opciones: Realm, ObjectBox, Core Data (iOS).

c) Bases de datos remotas mediante servicios web

Los datos se guardan en un servidor y la app se comunica con él por internet, normalmente con una API REST (peticiones HTTP que devuelven JSON). También existen servicios como Firebase (Firestore, Realtime Database) que ya incluyen la base de datos en la nube.

  • Permiten compartir la información entre varios usuarios y dispositivos.
  • Requieren conexión (o una estrategia de sincronización si se trabaja sin conexión).
Forma Ventajas Desventajas
Archivos Fáciles de usar; no necesitan servidor. No son buenos para consultas complejas ni muchos datos relacionados.
Base de datos local Consultas rápidas, funciona sin internet, datos organizados. Solo están en ese dispositivo; hay que manejar migraciones al cambiar la estructura.
Base de datos remota Datos centralizados y compartidos, respaldo en servidor. Depende de internet, latencia, requiere servidor y seguridad.

Tipos de datos almacenables según la forma de persistencia

Forma de persistencia Tipos de datos que se pueden guardar Ejemplos
SharedPreferences / DataStore Tipos primitivos: booleanos, enteros, flotantes, cadenas, conjuntos de cadenas. Nombre de usuario, idioma, modo oscuro.
Archivos (internos/externos) Texto, JSON, XML, imágenes, audio, video, PDF, datos binarios. Foto tomada, archivo de registro, documento descargado.
SQLite / Room INTEGER, REAL, TEXT, BLOB y NULL (las fechas y booleanos se guardan como número o texto). Lista de tareas, contactos, productos, historial.
Servicios web / nube Objetos JSON o XML, documentos, archivos, datos de usuarios. Perfil de usuario, publicaciones, pedidos.

Mecanismos de control de acceso a medios persistentes

1. Biblioteca de clases

Son conjuntos de clases ya hechas que facilitan guardar y leer datos sin escribir todo desde cero. En Android: SharedPreferences, DataStore, File, FileInputStream/FileOutputStream, y las librerías de Jetpack como Room. En iOS: UserDefaults, FileManager.

2. Clases de SQLite

Android incluye clases para trabajar directamente con SQLite:

  • SQLiteOpenHelper: crea la base de datos y controla sus versiones (onCreate, onUpgrade).
  • SQLiteDatabase: permite ejecutar SQL, insertar, actualizar, borrar y consultar.
  • ContentValues: guarda los pares columna-valor para insertar o actualizar.
  • Cursor: recorre los resultados de una consulta.

3. Mapeo relacional de objetos (ORM)

Un ORM (Object-Relational Mapping) convierte automáticamente las filas de las tablas en objetos del lenguaje (y al revés). Así se trabaja con clases en vez de escribir SQL para todo. Ejemplos: Room (Android), GreenDAO, Realm, Core Data / SwiftData (iOS). En Room se usan tres componentes principales:

  • @Entity: la clase que representa una tabla.
  • @Dao: la interfaz con las operaciones (insertar, consultar, borrar).
  • @Database: la clase que une todo y entrega los DAO.

Proceso de autenticación y consumo de servicios web en apps móviles

Autenticación es comprobar quién es el usuario. Un proceso típico es:

  1. El usuario escribe su correo y contraseña en la app.
  2. La app envía las credenciales al servidor por HTTPS.
  3. El servidor las valida y responde con un token (por ejemplo un JWT).
  4. La app guarda el token de forma segura (por ejemplo con EncryptedSharedPreferences).
  5. En cada petición posterior la app manda el token en el encabezado Authorization: Bearer ....
  6. El servidor verifica el token y devuelve los datos solicitados.
  7. Si el token expira, la app lo renueva (refresh token) o pide iniciar sesión otra vez.

Otras formas de autenticarse: OAuth 2.0 (iniciar con Google, Facebook), Firebase Authentication, biometría (huella o rostro) como paso adicional.

Consumo de un servicio web (API REST):

  1. Declarar el permiso de internet en el AndroidManifest.xml.
  2. Usar una librería HTTP como Retrofit u OkHttp (las llamadas deben hacerse fuera del hilo principal).
  3. Enviar la petición (GET, POST, PUT, DELETE) a la URL del servicio.
  4. Recibir la respuesta en JSON y convertirla en objetos (con Gson o Moshi).
  5. Mostrar los datos en la interfaz y manejar errores (sin conexión, error 401, 404, 500, etc.).

Ejemplos

Ejemplo 1: SharedPreferences

val prefs = getSharedPreferences("config", MODE_PRIVATE)

// Guardar
prefs.edit().putString("usuario", "Ana").putBoolean("modoOscuro", true).apply()

// Leer
val nombre = prefs.getString("usuario", "")

Ejemplo 2: escribir un archivo interno

openFileOutput("notas.txt", MODE_PRIVATE).use {
    it.write("Hola desde un archivo".toByteArray())
}

Ejemplo 3: SQLite con SQLiteOpenHelper

class AyudanteBD(context: Context) :
    SQLiteOpenHelper(context, "tareas.db", null, 1) {

    override fun onCreate(db: SQLiteDatabase) {
        db.execSQL("CREATE TABLE tareas (id INTEGER PRIMARY KEY AUTOINCREMENT, titulo TEXT)")
    }

    override fun onUpgrade(db: SQLiteDatabase, viejo: Int, nuevo: Int) {
        db.execSQL("DROP TABLE IF EXISTS tareas")
        onCreate(db)
    }
}

// Insertar
val valores = ContentValues().apply { put("titulo", "Estudiar") }
ayudante.writableDatabase.insert("tareas", null, valores)

Ejemplo 4: Room (ORM)

@Entity
data class Tarea(
    @PrimaryKey(autoGenerate = true) val id: Int = 0,
    val titulo: String
)

@Dao
interface TareaDao {
    @Insert
    suspend fun insertar(tarea: Tarea)

    @Query("SELECT * FROM Tarea")
    suspend fun obtenerTodas(): List<Tarea>

    @Delete
    suspend fun borrar(tarea: Tarea)
}

@Database(entities = [Tarea::class], version = 1)
abstract class AppDatabase : RoomDatabase() {
    abstract fun tareaDao(): TareaDao
}

Ejemplo 5: consumir una API con Retrofit

interface ApiServicio {
    @POST("login")
    suspend fun iniciarSesion(@Body datos: Credenciales): RespuestaLogin

    @GET("productos")
    suspend fun productos(@Header("Authorization") token: String): List<Producto>
}

val retrofit = Retrofit.Builder()
    .baseUrl("https://api.ejemplo.com/")
    .addConverterFactory(GsonConverterFactory.create())
    .build()

val api = retrofit.create(ApiServicio::class.java)
