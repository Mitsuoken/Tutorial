1. Control de versiones

Definición

El control de versiones es un sistema que registra los cambios realizados sobre un conjunto de archivos a lo largo del tiempo, de modo que se pueda recuperar una versión específica cuando se necesite. Se usa sobre todo para el código fuente, pero sirve para cualquier tipo de archivo.

Con un sistema de control de versiones se puede:

  • Regresar archivos o todo el proyecto a un estado anterior.
  • Comparar cambios hechos a lo largo del tiempo.
  • Saber quién modificó algo y cuándo.
  • Trabajar en equipo sin sobrescribir el trabajo de los demás.
  • Recuperarse fácilmente si se rompe o se pierde algo.

Tipos de sistemas de control de versiones

a) Sistemas locales

Guardan los cambios en una base de datos dentro de la misma computadora del usuario. Una forma muy básica es copiar carpetas con nombres como "proyecto_v1", "proyecto_v2_final". Un ejemplo de herramienta es RCS (Revision Control System), que guarda las diferencias entre versiones de cada archivo.

b) Sistemas centralizados (CVCS)

Existe un servidor central que guarda todas las versiones, y los desarrolladores descargan (checkout) los archivos que necesitan y suben (commit) sus cambios al servidor. Ejemplos: CVS, Subversion (SVN) y Perforce.

c) Sistemas distribuidos (DVCS)

Cada desarrollador tiene una copia completa del repositorio, con todo su historial, en su propia computadora. Se sincronizan entre sí mediante un repositorio remoto (por ejemplo GitHub, GitLab o Bitbucket). Ejemplos: Git, Mercurial y Bazaar.

Características, ventajas y desventajas

Tipo Características Ventajas Desventajas
Local (RCS) Todo se guarda en una sola computadora. Sin servidor ni red.
  • Muy sencillo de usar.
  • No necesita internet.
  • Rápido.
  • No sirve para trabajo en equipo.
  • Si falla el disco se pierde todo.
  • Funciones muy limitadas.
Centralizado (CVS, SVN, Perforce) Un servidor único guarda el historial. Los usuarios solo tienen la versión con la que trabajan.
  • Control claro de quién accede a qué.
  • Fácil de administrar.
  • Buen manejo de archivos grandes (Perforce).
  • Si el servidor cae, nadie puede guardar cambios ni ver el historial.
  • Si el servidor se daña sin respaldo, se pierde el historial.
  • Requiere conexión para casi todo.
  • Ramas más difíciles de manejar.
Distribuido (Git, Mercurial) Cada usuario tiene el repositorio completo. Se sincroniza con repositorios remotos.
  • Se puede trabajar sin conexión.
  • Ramas y mezclas (merge) rápidas y baratas.
  • Cada copia sirve como respaldo.
  • Flexible para distintos flujos de trabajo.
  • Curva de aprendizaje más alta.
  • Repositorios grandes ocupan más espacio local.
  • Puede haber conflictos de merge que resolver.
Nota: hoy en día Git es el sistema más usado, incluido el desarrollo móvil. Android Studio y Xcode lo tienen integrado.

Funcionamiento (ejemplo con Git)

En Git, los archivos pasan por tres áreas principales:

  1. Directorio de trabajo (working directory): donde se editan los archivos.
  2. Área de preparación (staging area): donde se eligen los cambios que irán en el siguiente commit.
  3. Repositorio local (.git): donde se guardan los commits (las "fotos" del proyecto).

Después los commits se envían a un repositorio remoto (GitHub, GitLab, etc.) con push y se traen los cambios de otros con pull o fetch.

Cada commit tiene un identificador único (hash), el autor, la fecha, un mensaje y apunta al commit anterior. Así se forma una cadena que representa el historial del proyecto.

Cómo se usa en el rastreo y gestión de cambios

Acción Comando en Git Para qué sirve
Ver el estadogit statusMuestra qué archivos cambiaron o están preparados.
Ver diferenciasgit diffMuestra línea por línea qué se modificó.
Ver historialgit logLista los commits con autor, fecha y mensaje.
Saber quién cambió una líneagit blame archivoMuestra el autor del último cambio de cada línea.
Crear ramasgit branch / git switchPermite trabajar en una función nueva sin afectar el código principal.
Unir ramasgit mergeIntegra los cambios de una rama en otra.
Deshacer un cambiogit revertCrea un commit que anula otro anterior.
Marcar versionesgit tag v1.0Etiqueta un punto del historial, por ejemplo una versión publicada.

En un proyecto móvil esto ayuda, por ejemplo, a tener una rama main con la versión publicada en la tienda de aplicaciones y ramas feature/... para cada función nueva.

Ejemplos

Ejemplo 1: iniciar un repositorio y hacer el primer commit

git init
git add .
git commit -m "Primer commit: proyecto base de la app"

Ejemplo 2: conectar con GitHub y subir

git remote add origin https://github.com/usuario/mi-app.git
git branch -M main
git push -u origin main

Ejemplo 3: crear una rama para una función nueva y mezclarla

git switch -c feature/login
# ... se hacen cambios ...
git add .
git commit -m "Agrega pantalla de login"
git switch main
git merge feature/login

Ejemplo 4: ver el historial resumido

git log --oneline
a3f9c21 Agrega pantalla de login
7b21e0d Primer commit: proyecto base de la app

Ejemplo 5: archivo .gitignore para Android

*.iml
.gradle/
/local.properties
/.idea/
/build/
/app/build/
.DS_Store

El .gitignore evita subir archivos generados o privados (por ejemplo local.properties, que tiene rutas de tu computadora).
